# 06. DB 스키마 운영 가이드
## 일본 골프 여행 가이드 웹앱

이 문서는 Supabase/PostgreSQL DB의 최종 스키마, 제약조건, 운영 규칙을 정의한다.

DB 구조를 변경하거나 CRUD를 작업하기 전에 반드시 이 문서를 먼저 읽는다.

---

# 1. 원칙

Supabase/PostgreSQL이 Single Source of Truth다.

- Google Sheets는 더 이상 데이터 저장소가 아니다.
- 모든 데이터는 PostgreSQL에 저장된다.
- 관리자 CRUD는 Supabase service-role client를 통해 직접 INSERT/UPDATE/DELETE한다.
- 고객 페이지는 Supabase anon client + RLS로 SELECT만 수행한다.
- Dual Read / Dual Write 금지 (Google Sheets와 DB를 동시에 읽거나 쓰지 않는다).

| FK | ON DELETE | 의미 |
|---|---|---|
| entities.area_id → areas.id | RESTRICT | 지역 삭제 시 엔티티가 있으면 차단 |

| restaurants.entity_id → entities.id | CASCADE | 엔티티 삭제 시 맛집 자동 삭제 |
| restaurant_locations.restaurant_entity_id → entities.id | CASCADE | 엔티티 삭제 시 관계 자동 삭제 |
| restaurant_locations.near_entity_id → entities.id | CASCADE | 엔티티 삭제 시 관계 자동 삭제 |
| travel_times.from_entity_id → entities.id | CASCADE | 엔티티 삭제 시 이동시간 자동 삭제 |
| travel_times.to_entity_id → entities.id | CASCADE | 엔티티 삭제 시 이동시간 자동 삭제 |
| faq.area_id → areas.id | RESTRICT | 지역 삭제 시 FAQ가 있으면 차단 |
| faq.category_id → categories.id | RESTRICT | 카테고리 삭제 시 FAQ가 있으면 차단 |
| faq.related_entity_id → entities.id | SET NULL | 엔티티 삭제 시 related만 해제 |
| content_sections.parent_entity_id → entities.id | CASCADE | 엔티티 삭제 시 섹션 자동 삭제 |
| includes_excludes.parent_entity_id → entities.id | CASCADE | 엔티티 삭제 시 항목 자동 삭제 |

핵심: entities 행을 DELETE하면 golf_courses, hotels, restaurants, content_sections, includes_excludes, restaurant_locations, travel_times가 CASCADE로 함께 삭제된다. areas나 categories는 RESTRICT로 보호된다.

# 8. RLS 정책

모든 11개 테이블에 RLS가 활성화되어 있다.

anon 역할에는 SELECT만 허용한다:

```sql
-- 모든 테이블에 동일 패턴
CREATE POLICY anon_select ON {table}
  FOR SELECT TO anon
  USING (true);
```

관리자 쓰기(INSERT/UPDATE/DELETE)는 service-role client를 사용한다. service-role은 RLS를 우회한다.

고객 페이지는 anon client로 SELECT만 수행하므로 RLS에 의해 읽기만 가능하다.

# 9. updated_at Trigger

모든 11개 테이블에 BEFORE UPDATE trigger가 설정되어 있다:

```sql
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

각 테이블:

```sql
CREATE TRIGGER set_{table}_updated_at
  BEFORE UPDATE ON {table}
  FOR EACH ROW
  EXECUTE FUNCTION set_updated_at();
```

코드에서 updated_at을 직접 설정할 필요 없다. UPDATE 시 자동 갱신된다.

단, Optimistic Concurrency Control을 위해 UPDATE 전에 현재 updated_at을 읽어서 클라이언트에 전달하고, UPDATE 시 WHERE 조건으로 비교한다.

# 10. Identifier 규칙

| 구분 | 용도 | 예시 |
|---|---|---|
| id | DB UUID (PK) | `b1fd38f0-261e-45de-b4bb-39ed87e5a211` |
| slug | URL/business identifier | `dos_golf_kaho` |
| code | area/category business code | `DOS`, `GOLF`, `HOTEL` |

규칙:

- id는 항상 DB가 생성하는 UUID다. 클라이언트가 임의 생성하지 않는다.
- slug는 entities 테이블에서 UNIQUE하다. URL 라우팅과 상세 페이지 조회에 사용된다.
- code는 areas, categories 테이블에서 UNIQUE하다. 비즈니스 로직에서 식별자로 사용된다.
- API 응답에는 id(UUID)와 slug를 모두 반환한다.
- UPDATE/DELETE는 id(UUID)를 기준으로 수행한다.
- URL 라우팅은 slug를 기준으로 수행한다.

# 12. Soft Delete 규칙

| 테이블 | 소프트 삭제 필드 | 방법 |
|---|---|---|
| areas | active | active = false |
| categories | active | active = false |
| entities | active | active = false (하위 테이블도 함께 비활성) |
| faq | active | active = false |
| travel_times | active | active = false |
| content_sections | is_visible | is_visible = false |
| includes_excludes | is_visible | is_visible = false |

관리자 UI에서는 "숨기기" 버튼으로 soft delete를 수행한다.

실제 DELETE(행 삭제)는 관리자가 명시적으로 "삭제" 버튼을 클릭할 때만 수행한다.

고객 페이지 쿼리에서는 active = true / is_visible = true 조건으로 필터링한다.

# 22. 드롭다운 필터링 규칙

관리자 화면에서 entity를 선택하는 드롭다운은 항상 다음 두 조건을 동시에 적용한다:

1. **현재 지역** (area): 현재 편집 중인 지역의 entity만 표시
2. **선택한 연결 유형** (entity_type): HOTEL/GOLF/RESTAURANT 등 선택한 유형만 표시

연결 유형을 변경하면:
- 기존 `related_entity_id` / `near_id` 즉시 초기화
- 새 유형에 맞는 목록만 다시 조회
- 목록이 없으면 빈 상태로 표시
- 다른 유형의 기존 값이 저장되지 않도록 방지

# 19. DB 변경 시 migration 작성 규칙

DB 스키마를 변경할 때는 반드시 migration 파일을 작성한다.

```text
supabase/migrations/{YYYYMMDD}_{description}.sql
```

예시:

```text
supabase/migrations/20260909_fix_faq_fk_and_check.sql
supabase/migrations/20260909_add_performance_indexes.sql
```

규칙:

- DDL(ALTER TABLE, CREATE INDEX 등)만 포함
- 멱등성 보장 (IF NOT EXISTS, IF EXISTS 사용)
- migration 적용 후 반드시 DB 메타데이터 재검증
- 코드에서 직접 DDL 실행하지 않고 migration 파일로 관리한다

# 20. Production CRUD/F5 검증 절차

DB 스키마 변경 또는 CRUD 코드 수정 후 반드시 아래 절차를 수행한다.

## 검증 대상 (8개 resource)

1. Category (areas + categories)
2. Golf (entities + golf_courses)
3. Hotel (entities + hotels)
4. Restaurant (entities + restaurants + restaurant_locations)
5. FAQ (faq)
6. Content Section (content_sections)
7. Includes/Excludes (includes_excludes)
8. Travel Time (travel_times)

## 각 resource별 검증 단계

1. CREATE → 201 응답 + UUID 반환 확인
2. UPDATE → 같은 UUID로 수정 + 200 응답
3. F5 READ → GET 호출로 생성/수정된 데이터 확인
4. 새 탭 → 브라우저 새 탭에서 동일 데이터 확인
5. DELETE → 같은 UUID로 삭제 + 200 응답

## 주의사항

- Golf/Hotel/Restaurant의 last_verified는 빈 문자열이 아닌 null을 저장한다
- Hotel의 has_public_bath, has_outdoor_onsen, has_sauna는 DB boolean이다. 빈 문자열("")을 저장하지 않는다.
- Restaurant의 recommended는 DB boolean이다. 빈 문자열을 저장하지 않는다.
- TravelTime 신규 생성 시 active 기본값은 true다
- FAQ area 비교는 case-insensitive로 처리한다
- restaurant_locations join 결과는 null guard가 필요하다

## DB canonical type vs UI/API compatibility

DB의 boolean 컬럼은 실제 PostgreSQL boolean이다.

일부 UI/API compatibility layer에서 `"TRUE"` / `"FALSE"` / `""` 문자열을 사용하는 구간이 있다.

- DB canonical type = boolean (true / false / null)
- UI/API legacy shape = `"TRUE"` / `"FALSE"` / `""` (문자열)

변환 위치: `src/lib/supabase-cms.ts`의 `mapHotel`, `mapRestaurant`, `isActive` 함수에서 DB boolean ↔ 문자열 변환을 수행한다.
